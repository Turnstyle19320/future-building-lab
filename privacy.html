Local Storage, Cloud Storage, and Student Data

Most classroom prototypes can stay simple and local. The risk changes when data leaves the learner's device, gets tied to identity, or becomes part of a shared record.

This page is a decision guide, not legal advice. If a tool stores student names, grades, behavior notes, uploads, roster data, or shared records, use your district's approved process before putting it in front of students.
Fast read

Risk rises when data starts to persist, travel, or identify a student.

Usually safe to prototype

No storage, demo data, anonymous practice, one-device activities.

Slow down and check

Local saves, join codes, nicknames, temporary group activity data.

Use the approved path

Names, grades, rosters, behavior notes, uploads, teacher dashboards.

The simple mental model

Where does the data live?

That one question determines most of the next questions. A static tool with no storage is different from local browser storage, which is different from a cloud database.

No saved data
Safest first build No persistence No identity needed

What it means: The page runs in the browser and forgets everything when refreshed or closed.

Good for: simulations, calculators, flashcards, prompt generators, reflection starters, timers, randomizers, and practice activities.

Teacher-friendly rule: If the tool does not collect or save student information, it is usually the safest first prototype.

Local browser storage
One browser Good for drafts Not a record system

What it means: The browser stores data on the same device and same site origin. In a simple prototype, nothing is automatically sent to a server just because you used localStorage.

Good for: one-device demos, personal checklists, draft reflections, local practice logs, and "try it today" tools where the saved data does not need to follow a student across devices.

Limits: Local storage is not a secure student record system. It can be cleared by the browser, stays tied to that browser/device, and should not be used for sensitive records.

  • Use demo data or nicknames when possible.
  • Avoid grades, behavior records, medical details, IEP/504 details, and discipline notes.
  • Tell users when data is saved locally.
Temporary join codes or local network tools
Live activity Temporary data Ask what persists

What it means: A tool may use a small server process, such as Node.js, to connect devices with a join code during a live activity.

Good for: live group demos, anonymous polling, collaborative prototyping, or one-session activities where data is not permanently stored.

Questions to answer: Is anything written to disk? Is anything sent outside the local network? Are student identities attached? How long does the session data persist?

Teacher-friendly rule: A join code is not automatically a privacy problem. Persistent records, identity, and external hosting are what raise the stakes.

Cloud database or server storage
Third party Cross-device District approval

What it means: Data is stored on an external service, such as a hosted database, serverless storage, Cloudflare Workers/KV/D1, Firebase, Supabase, or another backend.

Good for: real multi-user apps, cross-device history, teacher dashboards, shared records, and tools that need accounts.

Why the risk changes: Once identifiable student data is stored by a third-party service, schools need to consider FERPA, district vendor approval, contracts, access controls, retention, deletion, and who can see the data.

  • Do not store student names, grades, rosters, or behavior data in an unapproved cloud service.
  • Do not add logins or uploads casually.
  • Use district-approved platforms when the data becomes an education record.
Public static hosting
Publishes files Great for browser tools Not private storage

What it means: GitHub Pages or similar static hosting publishes files like index.html, style.css, script.js, and images. It is excellent for tools that run entirely in the browser.

Good for: public resources, simulations, class tools, portfolios, workshop sites, and apps that do not require private server-side data.

Boundary: Public static hosting is not private student-data infrastructure. If the tool needs private data, accounts, or a database, the project has moved beyond a static site.

Quick decision check

Four questions before the tool goes live.

If the answer moves rightward, the project needs more care. The issue is rarely the code by itself; it is persistence, identity, and access.

1

Does it save anything?

No saved data keeps most prototypes simple.

2

Is it tied to identity?

Names, emails, IDs, and rosters raise the stakes.

3

Does it leave the device?

External storage changes who can access the data.

4

Could it become a record?

Grades, behavior, accommodations, and dashboards need the approved process.
